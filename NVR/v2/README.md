# Keenetic NVR — резервный видеорегистратор с гибкой глубиной архива

> **Основной репозиторий:** [saymer-alt/keenetic-nvr](https://github.com/saymer-alt/keenetic-nvr).
> Проект выделен из [keenetic-knowledge-base](https://github.com/saymer-alt/keenetic-knowledge-base); историю переноса см. в [REPOSITORY-EXTRACTION.md](REPOSITORY-EXTRACTION.md).

**Проверенная аппаратно база: v2.4, KN-1012 (10.10.2026).**
**NVR v2.5: частичная аппаратная приёмка TIME/72h на KN-1012 (18.10.2026)** — три камеры HEALTHY, новые MKV на существующем EXT4, `cleanup --dry-run` 276 кандидатов без ошибок, реальный `cleanup` 276 удалений (около 14.9 GB свободного пространства), watchdog/cron восстановлены, Telegram-уведомления доставлены, команды `/status`, `/cameras`, `/disk`, `/help` **PASS 4/4**. Подробно: [финальный протокол восстановления](../../FIELD-ACCEPTANCE-2026-10-18.md).

**Это не полная приёмка v2.5:** первое самостоятельное почасовое срабатывание cleanup после восстановления пока не наблюдалось; reboot/recovery, USB-loss, принудительные сбои, режимы CIRCULAR/HYBRID и чистая установка на тестовом USB ещё не проверены. См. [#7](https://github.com/saymer-alt/keenetic-nvr/issues/7). Основной аппаратный регистратор работает независимо: резервный NVR сохраняет копию архива на Keenetic.

## NAND-safe /opt и восстановление после смены Mesh

Для `/opt` на внутренней UBIFS частое состояние Telegram-бота должно
находиться на выделенном внешнем EXT4-диске, а не в `/opt/var/lib`.
Новый storage guard проверяет наиболее глубокую точку монтирования,
сам архивный USB и отсутствие ссылок в `/opt`. При отсутствующем USB
бот не подтверждает команды; запуск записи и удаление тоже блокируются.

При наличии старых MKV «чистый» мастер установки **отказывает**
в запуске. Обязательно используйте [сценарий восстановления после
замены контроллера Mesh](MESH-RECOVERY.md), не форматируйте архив.
Код ещё не проходил отдельные аппаратные NAND/USB-failure испытания.

### Дополнительная защита NAND

Для внутренней `/opt` NVR требует защитный `nvr-storage-guard.sh`:
при его отсутствии не считает архив безопасным для записи. Каталог
частых PID/lock/check/tmp `NVR_STATE_DIR` обязан находиться в RAM
`/tmp` с реальной ФС `tmpfs`; ссылки из него в постоянную память
запрещены. `TMPDIR` принудительно направлен в `/tmp`.

На внешнем USB EXT4 остаются MKV, журнал FFmpeg и долговременная
метаинформация Telegram. Telegram не принимает перенаправление
состояния в UBIFS и не следует символической ссылке на каталог
состояния. Эти изменения не переустанавливают Entware. **Свежий установщик
NVR теперь автоматически подключает оригинальную `S00ubifs` из
KAS/stable при внутреннем /opt** в режимах установки/настройки,
но не в read-only preflight. Как и ранее, не запускайте fresh-install
поверх сохранившихся MKV: это отдельный сценарий восстановления. Полная схема и read-only аудит:
[защита NAND на двух KN-1012](../../NAND-WEAR.md).

## Новые режимы записи/хранения (v2.5)

- **TIME** — сохраняет выбранный минимум часов без досрочного удаления
  (по умолчанию 72 часа даже для старых конфигураций).
- **CIRCULAR** — удаляет самые старые завершённые MKV при нехватке
  свободного места, резерв по умолчанию 10% / минимум 128 МБ.
- **HYBRID** — удаляет записи по возрасту и досрочно при заполнении.
  Важное отличие: **заданные часы — верхняя граница, не гарантия минимума**.
- Мастер `fresh-install.sh` предлагает выбор политики и требует
  написать `DELETE` перед разрешением досрочного удаления.
- `nvr cleanup --dry-run` показывает кандидатов на удаление,
  ничего не удаляя; `/status` и `/disk` выводят режим и резерв.
- CIRCULAR/HYBRID запускают cleanup каждые 5 минут при новой установке.
- [Подробное описание режимов и ограничения](STORAGE-MODES.md).

**Предупреждение:** **TIME/72h уже аппаратно проверен** на KN-1012
18.10.2026, включая реальное удаление 276 истёкших MKV после dry-run.
Но CIRCULAR/HYBRID и fresh-install на отдельном тестовом USB ещё
не проверены; для важных архивов выбирайте TIME/72h.

## Функциональный контракт (не ослабляется)

- Три RTSP-канала `101`, `201`, `301` (список настраивается), папки `cctv/cam101`, `cam201`, `cam301`.
- `FFmpeg -c copy` — H.265/H.264 без перекодирования; нарезка MKV по 900 секунд
  (фактический разрез зависит от ключевых кадров).
- В **TIME** каждый завершённый сегмент хранится не менее заданного срока
  (по умолчанию 72 часа) от `mtime`, очистка по Cron выполняется ежечасно.
  В **CIRCULAR/HYBRID** досрочное удаление разрешено только явным выбором.
  Текущий открытый сегмент не удаляется.
- **TIME не удаляет записи раньше срока даже при заполнении.**
  В остальных режимах старые завершённые MKV могут удаляться ради места.
  Пороговые WARN/CRITICAL о заполнении остаются.
- Каждые 5 минут проверяется каждый поток: жив ли FFmpeg и обновляется ли файл.
  Перезапускается только отказавшая камера, с нарастающей задержкой повторов.
- Дополнительный прогноз: если свободного места меньше, чем потребуется на 72 часа
  при текущем битрейте (по данным последнего часа записи), — WARN. Без данных
  прогноз не делается.
- Все секреты — только локально в `/opt/etc/nvr-v2.conf` (mode 600). В репозитории —
  только пример без секретов.

## Команды

Все команды: `sh /opt/etc/nvr-v2.sh <команда>` (в примерах ниже — `nvr`).

| Команда | Действие |
| --- | --- |
| `nvr status` | Состояние: диск, глубина архива, последняя очистка, каждая камера |
| `nvr check` | Один цикл проверки/восстановления (обычно запускает cron) |
| `nvr cleanup` | Один проход очистки выбранной политики хранения |
| `nvr cleanup --dry-run` | Просмотр кандидатов без удаления файлов и обновления истории очистки |
| `nvr logs [N]` | Последние N строк журнала событий (по умолчанию 50), секреты скрыты |
| `nvr logs cam101` | Хвост FFmpeg-лога камеры 101, RTSP-URL скрыт |
| `nvr notify test` | Тестовое уведомление в настроенные каналы |
| `nvr stop` | **Долгая остановка**: камеры останавливаются, cron не перезапустит их до `start`/`resume`; переживает перезагрузку |
| `nvr pause` | Синоним `stop` |
| `nvr start` | Снять паузу и запустить запись немедленно (сбрасывает задержки повторов) |
| `nvr resume` | Синоним `start` |

Раньше обычный `stop` перезапускался cron'ом в течение 5 минут. Начиная с v2.4
`stop`/`pause` — это явное намерение владельца: маркер паузы пишется на архивный диск
и переживает перезагрузку; `check` при паузе ничего не делает. Автономное
восстановление после перезагрузки работает само: cron поднимает камеры в течение
5 минут после старта роутера, когда диск смонтирован.

Пример `nvr status`:

```text
NVR v2.5 - HEALTHY
DISK: RW, 20% used, 499.0 GB free
STORAGE MODE: time
RETENTION: 72 hours
SEGMENT: 900 seconds
LAST CHECK: 2026-10-09 22:05:01 (85s ago)
LAST CLEANUP: 2026-10-09 22:03:01 OK
LAST SUCCESSFUL CLEANUP: 2026-10-09 22:03:01
REMOVED FILES: 0 (skipped 0)
CAM 101: HEALTHY, last write 2s ago
CAM 201: HEALTHY, last write 6s ago
CAM 301: HEALTHY, last write 2s ago
ALERTS: disabled
```

В режимах `circular`/`hybrid` вместо строки `RETENTION: … hours` выводится
`RETENTION: capacity-based (no minimum)` и добавляется строка
`FREE RESERVE: <N>% (minimum <M> MB)`.

Состояния камеры: `HEALTHY`, `STARTING` (процесс есть, первого файла ещё нет),
`STALE` (процесс есть, данные не обновляются), `DOWN` (процесса нет),
`STOPPED` (пауза/остановлена), `UNKNOWN` (диск недоступен или ошибка stat).
Успешная очистка с нулём удалённых файлов — норма, а не ошибка
(`CLEANUP RESULT: OK`, «REMOVED FILES: 0»).

## Уведомления (необязательный модуль)

Без настройки NVR работает полностью автономно (`ALERTS: disabled`). При настройке
NVR отправляет:

| Событие | Уровень |
| --- | --- |
| Диск заполнен на 75% | WARN |
| Диск заполнен на 90% | CRITICAL |
| Камера длительно не пишет | ERROR |
| Watchdog не смог восстановить камеру (после нескольких попыток) | ERROR |
| Камера снова пишет (после подтверждения свежего файла) | RECOVERY |
| Носитель отключён, недоступен или read-only | CRITICAL |
| Очистка не выполняется дольше допустимого интервала (по умолчанию 2 часа) | WARN |
| Свободного места меньше прогноза на 72 часа при текущем битрейте | WARN |

Транспорты: Telegram Bot API (`NVR_NOTIFY_TELEGRAM_TOKEN` + `NVR_NOTIFY_TELEGRAM_CHAT`)
и/или универсальный HTTPS webhook (`NVR_NOTIFY_WEBHOOK_URL`, POST JSON
`{"level","key","text"}`, успех — любой HTTP 2xx).

- Дедупликация по инциденту: повторные уведомления по тому же инциденту — не чаще
  `NVR_NOTIFY_REPEAT_SECONDS` (по умолчанию 21600 = 6 часов). RECOVERY отправляется
  только после подтверждённого восстановления и только если инцидент был открыт.
- Токены хранятся только в `/opt/etc/nvr-v2.conf` (mode 600) и передаются в curl
  через stdin-конфиг (`curl -K -`), поэтому не видны в `ps` и не попадают в журналы.
- Ошибка доставки не влияет на запись; неудачная попытка повторяется через интервал.
- `nvr notify test` проверяет доставку и показывает HTTP-коды ответов.
- Если NVR не может отправить уведомление (отключён WAN/роутер/электричество),
  **локальная отправка не гарантирует доставку** именно в тот момент, когда всё
  остальное тоже отключилось. Для контроля «жив ли NVR» извне предусмотрен
  внешний heartbeat через VPS — отдельный вариант, в релиз не входит
  (см. KNOWN-LIMITATIONS.md).

Настройка: интерактивный установщик спрашивает про уведомления при `install-fresh`
(токен вводится скрыто). Для уже установленного NVR v2.4/v2.5 предусмотрен
**короткий мастер**, без копирования длинного here-document в SSH.

1. В Telegram через `@BotFather` выполнить `/newbot` и получить **API token**
   (цифры, двоеточие, буквенно-цифровая строка). Это не `@username` и не
   полный текст ответа BotFather. Токен никогда не пересылать другим лицам.
2. Открыть созданного бота, нажать «Запустить», отправить `/start` и ещё
   одно сообщение. Это нужно для определения Chat ID.
3. На роутере запустить:

```sh
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-nvr/main/NVR/v2/telegram-setup.sh -o /tmp/nvr-telegram-setup.sh
sh -n /tmp/nvr-telegram-setup.sh && sh /tmp/nvr-telegram-setup.sh
```

Токен вводится **скрыто**, передаётся в Telegram API через stdin `curl -K -`,
Мастер сначала показывает `@username` бота из Telegram `getMe`, чтобы можно
сверить его с открытым чатом. Chat ID определяется через `getUpdates`;
если обновлений нет, мастер предложит послать новое сообщение правильному
боту и повторит попытку. При повторной неудаче доступен ручной ввод
числового Chat ID с подтверждением пользователя.
Мастер сохраняет приватную резервную копию конфига с правами 600, атомарно
обновляет `/opt/etc/nvr-v2.conf` и выполняет `notify test`. При недоступном
Telegram запись камер не останавливается. Не публиковать токен, конфиг и
полные команды HTTP-запросов.

Для проверки: `sh /opt/etc/nvr-v2.sh status` и
`sh /opt/etc/nvr-v2.sh notify test`. Если у бота включён webhook,
`getUpdates` может быть недоступен: потребуется ручное указание Chat ID.

## Telegram: статус по запросу из чата

После подключения аварийных Telegram-уведомлений можно отдельно включить
**приём команд**. Он не включается автоматически: бот NVR отвечает только
на запросы из заранее настроенного *приватного чата* и не позволяет менять
состояние записи, останавливать камеры или удалять архив.

| Команда в Telegram | Ответ |
| --- | --- |
| `/status` | Общий HEALTHY/DEGRADED/PAUSED, камера 101/201/301, диск, последняя проверка и очистка |
| `/cameras` | Состояние записи и возраст последнего MKV по каждой камере |
| `/disk` | Свободное место, политика хранения 72 ч, очистка |
| `/help` или `/start` | Доступные команды |

Для обычного Keenetic за NAT входящий веб-сервер не нужен. Скрипт
`telegram-bot.sh` раз в минуту опрашивает Telegram Bot API `getUpdates` через
HTTPS, выполняет только **read-only** `sh /opt/etc/nvr-v2.sh status`,
отправляет ответ через `sendMessage` и сохраняет последний `update_id`
в состоянии бота (сохраняется после перезагрузки): `/opt/var/lib/nvr-telegram/`
на внешнем EXT4 `/opt`, либо — при внутренней UBIFS — в `.nvr-v2/telegram`
на архивном EXT4-диске (никогда во внутреннюю NAND; подробности:
[NAND-WEAR.md](../../NAND-WEAR.md)).
Токен берётся из уже настроенного `/opt/etc/nvr-v2.conf`, повторно вводить не надо.

### Включение на уже работающем NVR v2.4/v2.5

Зависимость для безопасного разбора Telegram JSON:

```sh
opkg update
opkg install jq
```

Загрузить небольшой установщик и проверить требования:

```sh
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-nvr/main/NVR/v2/telegram-bot-install.sh -o /tmp/nvr-telegram-bot-install.sh
sh -n /tmp/nvr-telegram-bot-install.sh
sh /tmp/nvr-telegram-bot-install.sh preflight
```

После `PASS` включить:

```sh
sh /tmp/nvr-telegram-bot-install.sh install
```

Добавляется только одна строка root Cron:

```cron
* * * * * /bin/sh /opt/etc/nvr-telegram-bot.sh poll
```

**После установки** подождать минуту и отправить `/status` боту,
который ранее прислал сообщение `NVR TEST`. Исторические сообщения
не воспроизводятся: установщик инициализирует offset через `getUpdates`.
Задержка ответа обычно до 1 минуты, зависит от Cron и связи.

Диагностика и отключение:

```sh
sh /tmp/nvr-telegram-bot-install.sh status
sh /opt/etc/nvr-telegram-bot.sh status
crontab -l | grep nvr-telegram-bot
sh /tmp/nvr-telegram-bot-install.sh remove
```

Отключение модуля команд не отключает **аварийные Telegram-уведомления**
или запись камер. При ошибках `getUpdates` проверяйте наличие webhook или
другого процесса, который опрашивает **того же бота**: Telegram не гарантирует
корректную работу нескольких независимых потребителей очереди обновлений.
Пароли, токены и локальный конфиг не выкладывайте в GitHub.

## Установка с нуля (другой Keenetic, без старого NVR)

Требования: Keenetic с **уже установленным Entware**, отдельный USB-накопитель
**EXT4** (не системный диск Entware), интерактивная SSH-сессия (`ssh -t`).
Мастер выбирает доступный RW-диск; тип файловой системы EXT4 нужно
обеспечить заранее.

**Одна команда для новой установки** (аналогично keenetic-auto-setup):

```sh
opkg update && opkg install curl && \
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-nvr/main/setup.sh | sh
```

Корневой `setup.sh` проверяет Entware и терминал, скачивает
`NVR/v2/bootstrap.sh` из текущего репозитория, проверяет его синтаксис
и запускает **`install-fresh`**. Никакие RTSP-пароли не вводятся в командной
строке. Для выбора диска и скрытого ввода пароля скрипты читают
`/dev/tty`, поэтому `curl | sh` совместим с интерактивным мастером.
Отказ скачивания виден как ошибка curl, но exit-код всей цепочки
`curl | sh` не всегда отражает эту ошибку: для контролируемого запуска
скачайте файл отдельно:

```sh
opkg update && opkg install curl && \
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-nvr/main/setup.sh -o /tmp/nvr-setup.sh && \
sh -n /tmp/nvr-setup.sh && sh /tmp/nvr-setup.sh
```

При наличии `/opt/etc/nvr-v2.sh` или `/opt/etc/nvr-v2.conf`
`setup.sh` отказывается переустанавливать NVR — работающие камеры
не будут случайно прерваны.

**Только preflight**, без настройки записи (`prerequisites` может
предложить установить недостающие Entware-пакеты с подтверждением):

```sh
sh /tmp/nvr-setup.sh preflight
```

### Ручной способ через bootstrap.sh (для диагностики)

1. Компоненты (установщик предложит установить сам, но можно заранее):

```sh
opkg update
opkg install ffmpeg cron curl coreutils-stat
```

2. Загрузить установщик и проверить окружение (ничего не меняет):

```sh
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-nvr/main/NVR/v2/bootstrap.sh -o /tmp/nvr-install.sh
sh /tmp/nvr-install.sh preflight-fresh
```

Установщик по умолчанию загружает остальные компоненты из `main`
**этого репозитория**. Для воспроизводимого развертывания можно закрепить
конкретный commit SHA через переменную `NVR_RAW_BASE`.
Старые URL из базы знаний оставлены доступными для уже установленного NVR.

3. Установка:

```sh
sh /tmp/nvr-install.sh install-fresh
```

Мастер на самом роутере: выбор диска из реально смонтированных (системный диск
Entware отвергается) → RTSP-адрес (IP/имя, без `rtsp://` и порта) → логин →
**пароль со скрытым вводом** → каналы (Enter = `101 201 301`) → необязательная
настройка уведомлений. Затем: конфиг `/opt/etc/nvr-v2.conf` (mode 600), старт
FFmpeg, проверка появления свежих MKV каждой камерой (до 60 секунд) и только
потом cron. Cron-задачи других программ не затрагиваются.

**Специальные символы в пароле.** Если пароль содержит `@ : / ? #` и подобные
символы, установщик сам проверит оба варианта URL (как есть и с
процент-кодированием) и сохранит рабочий (`NVR_RTSP_ENCODE`). Буквальный `%`
остаётся как набран в обоих вариантах. Если ни один вариант не подошёл —
используйте отдельную учётную запись камеры с паролем без URL-спецсимволов.

4. Повторная настройка без переустановки (смена пароля/камер):

```sh
sh /opt/etc/nvr-v2.sh stop
sh /tmp/nvr-install.sh configure-fresh
sh /tmp/nvr-install.sh install-fresh
```

## Миграция с NVR v1 (тот же роутер, кнопка `switch`)

Для заранее диагностированного роутера (путь диска совпадает с указанным в
`install-router.sh`): preflight проверяет FFmpeg, `stat`, RW-диск и отсутствие
живых legacy-процессов **до** любых изменений; исходные `S99cctv`, `record_cctv.sh`,
crontab-ы сохраняются в `/opt/etc/nvr-v2-backup`; RTSP-параметры извлекаются из
старого скрипта локально; при сбое — автоматический откат.

```sh
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-nvr/main/NVR/v2/bootstrap.sh -o /tmp/nvr-install.sh
sh /tmp/nvr-install.sh preflight   # только проверка
sh /tmp/nvr-install.sh switch      # переключение
sh /opt/etc/nvr-v2-backup/rollback.sh rollback   # откат, если понадобится
```

После миграции пароль камеры рекомендуется сменить (он уже встречался в старом
скрипте и истории команд) и обновить локально в `/opt/etc/nvr-v2.conf`.

## Обновление работающей v2.3 до v2.4

**Нельзя** обновлять старым способом `stop → curl -o /opt/etc/nvr-v2.sh → start`:
v2.3 не блокирует автоматический перезапуск через cron после `stop`.
Для обновления добавлен `upgrade-router.sh` с отдельным бэкапом, временным
отключением только NVR Cron, проверкой трёх камер и автоматическим откатом.

Для уже работающей **v2.3** (это не команда переустановки v2.4)
используйте опубликованный загрузчик:

```sh
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-nvr/main/NVR/v2/bootstrap.sh -o /tmp/nvr-upgrade.sh
sh /tmp/nvr-upgrade.sh preflight-upgrade
```

Только после успешного preflight можно выполнять переключение:

```sh
sh /tmp/nvr-upgrade.sh upgrade
```

Резервная копия старого скрипта и полного исходного root crontab:
`/opt/etc/nvr-v24-upgrade-backup/`. Обновление не редактирует
`/opt/etc/nvr-v2.conf`, не удаляет MKV и не затрагивает чужие Cron-задачи.
При неудаче установщик пытается автоматически откатиться.

```sh
sh /opt/etc/nvr-v24-upgrade-backup/rollback.sh rollback
```

Ручной rollback возвращает снимок root crontab: проверьте, что после
обновления в нём не появились новые, не включённые в бэкап задания.
Обновление v2.3 → v2.4 реально выполнено 10.10.2026 на KN-1012
с сообщением `NVR upgrade PASS` и подтверждённой записью трёх камер.
Воспроизведение отката при ошибке **отдельно не тестировалось**.
Для воспроизводимого обновления фиксируйте commit SHA через `NVR_RAW_BASE`,
а не постоянно движущуюся ветку.

## Диагностика типовых ситуаций

- `CAM 101: DOWN` дольше 30 минут → смотреть `nvr logs cam101` и `nvr status`;
  проверить доступность камеры с роутера (`ping`), учётные данные, не занят ли
  канал другим recorder'ом.
- `DISK: NOT MOUNTED/READ-ONLY` → проверьте `mount | grep /tmp/mnt`, файловую
  систему (`dmesg`), кабель/питание USB. Запись и удаление блокируются до
  восстановления RW.
- `LAST CLEANUP: ... FAILED` → обычно совпадает с недоступностью диска;
  повторное выполнение по cron вернёт `OK`.
- `ALERTS: enabled`, но уведомлений нет → `nvr notify test` покажет HTTP-код;
  проверьте токен/chat ID, доступ роутера к api.telegram.org.
- Полный журнал: `nvr logs 200`; место на диске: `df -h /tmp/mnt/<UUID>`.

## Удаление NVR (видеозаписи остаются)

```sh
sh /opt/etc/nvr-v2.sh stop
crontab -l | grep -v 'nvr-v2.sh' | crontab -   # убрать только задания NVR
/opt/etc/init.d/S10cron restart
rm /opt/etc/nvr-v2.sh /opt/etc/nvr-v2.conf
rm -rf /tmp/nvr-v2
# Архив остаётся: /tmp/mnt/<UUID>/cctv/cam*/...mkv — удалить отдельно, если нужно.
```

Для миграции на v1 вместо удаления используйте `rollback` (см. выше).

## Безопасность и секреты

- `/opt/etc/nvr-v2.conf` — mode 600, root-only; токены и RTSP-пароли только там.
- Журналы (`nvr logs`, ротация логов) пропускают RTSP-URL через редактирование:
  `rtsp://…@` → `rtsp://[REDACTED]@`.
- **Известное ограничение:** RTSP-URL с паролем виден в `/proc/<pid>/cmdline`
  процесса FFmpeg любому локальному пользователю с правом чтения `/proc`
  (на Keenetic это root). Ограничение платформы FFmpeg; снижение риска —
  отдельная ограниченная учётная запись только для RTSP. Не публикуйте `ps w`,
  логи камер и содержимое конфига.
- CI репозитория выполняет: синтаксис POSIX sh + BusyBox ash, ShellCheck
  (errors), офлайн-тесты, сканер секретов (токены Telegram, RTSP-URL
  с паролями, приватные ключи).
