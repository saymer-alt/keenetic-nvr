# Keenetic NVR v2.4 — резервный видеорегистратор 72 часа на камеру

**Статус: candidate v2.4.** Офлайн-тесты BusyBox ash и ShellCheck проходят (CI в репозитории).
Переход на v2.3 на KN-1012 выполнен 2026-10-09 (FFmpeg 6.1.4, три камеры пишут MKV,
cron health-check подтверждён). Часть проверок v2.4 (см. «Что осталось проверить на живом
роутере») ещё не выполнена. Основной аппаратный регистратор работает независимо —
NVR существует, чтобы сохранить архив, если основной регистратор украден или отключён.

## Функциональный контракт (не ослабляется)

- Три RTSP-канала `101`, `201`, `301` (список настраивается), папки `cctv/cam101`, `cam201`, `cam301`.
- `FFmpeg -c copy` — H.265/H.264 без перекодирования; нарезка MKV по 900 секунд
  (фактический разрез зависит от ключевых кадров).
- **Каждый завершённый сегмент хранится не менее 72 часов** от последней записи в файл
  (`mtime`). Очистка раз в час → фактическая глубина 72–73 часа. Текущий открытый
  сегмент не удаляется никогда.
- **Не удалять видео моложе 72 часов ради освобождения места.** Заполнение диска —
  только предупреждения: WARN при 75%, CRITICAL при 90%.
- Каждые 5 минут проверяется каждый поток: жив ли FFmpeg и обновляется ли файл.
  Перезапускается только отказавшая камера, с нарастающей задержкой повторов.
- Дополнительный прогноз: если свободного места меньше, чем потребуется на 72 часа
  при текущем битрейте (по данным последнего часа записи), — WARN. Без данных
  прогноз не делается.
- Все секреты — только локально в `/opt/etc/nvr-v2.conf` (mode 600). В репозитории —
  только пример без секретов.

## Команды

Все команды: `sh /opt/etc/nvr-v2.sh <команда>` (в примерах ниже — `nvr`).

| Команда | Действие |
| --- | --- |
| `nvr status` | Состояние: диск, глубина архива, последняя очистка, каждая камера |
| `nvr check` | Один цикл проверки/восстановления (обычно запускает cron) |
| `nvr cleanup` | Один проход очистки по 72-часовому горизонту |
| `nvr logs [N]` | Последние N строк журнала событий (по умолчанию 50), секреты скрыты |
| `nvr logs cam101` | Хвост FFmpeg-лога камеры 101, RTSP-URL скрыт |
| `nvr notify test` | Тестовое уведомление в настроенные каналы |
| `nvr stop` | **Долгая остановка**: камеры останавливаются, cron не перезапустит их до `start`/`resume`; переживает перезагрузку |
| `nvr pause` | Синоним `stop` |
| `nvr start` | Снять паузу и запустить запись немедленно (сбрасывает задержки повторов) |
| `nvr resume` | Синоним `start` |

Раньше обычный `stop` перезапускался cron'ом в течение 5 минут. Начиная с v2.4
`stop`/`pause` — это явное намерение владельца: маркер паузы пишется на архивный диск
и переживает перезагрузку; `check` при паузе ничего не делает. Автономное
восстановление после перезагрузки работает само: cron поднимает камеры в течение
5 минут после старта роутера, когда диск смонтирован.

Пример `nvr status`:

```text
NVR v2.4 - HEALTHY
DISK: RW, 20% used, 499.0 GB free
RETENTION: 72 hours
SEGMENT: 900 seconds
LAST CHECK: 2026-10-09 22:05:01 (85s ago)
LAST CLEANUP: 2026-10-09 22:03:01 OK
LAST SUCCESSFUL CLEANUP: 2026-10-09 22:03:01
REMOVED FILES: 0 (skipped 0)
CAM 101: HEALTHY, last write 2s ago
CAM 201: HEALTHY, last write 6s ago
CAM 301: HEALTHY, last write 2s ago
ALERTS: disabled
```

Состояния камеры: `HEALTHY`, `STARTING` (процесс есть, первого файла ещё нет),
`STALE` (процесс есть, данные не обновляются), `DOWN` (процесса нет),
`STOPPED` (пауза/остановлена), `UNKNOWN` (диск недоступен или ошибка stat).
Успешная очистка с нулём удалённых файлов — норма, а не ошибка
(`CLEANUP RESULT: OK`, «REMOVED FILES: 0»).

## Уведомления (необязательный модуль)

Без настройки NVR работает полностью автономно (`ALERTS: disabled`). При настройке
NVR отправляет:

| Событие | Уровень |
| --- | --- |
| Диск заполнен на 75% | WARN |
| Диск заполнен на 90% | CRITICAL |
| Камера длительно не пишет | ERROR |
| Watchdog не смог восстановить камеру (после нескольких попыток) | ERROR |
| Камера снова пишет (после подтверждения свежего файла) | RECOVERY |
| Носитель отключён, недоступен или read-only | CRITICAL |
| Очистка не выполняется дольше допустимого интервала (по умолчанию 2 часа) | WARN |
| Свободного места меньше прогноза на 72 часа при текущем битрейте | WARN |

Транспорты: Telegram Bot API (`NVR_NOTIFY_TELEGRAM_TOKEN` + `NVR_NOTIFY_TELEGRAM_CHAT`)
и/или универсальный HTTPS webhook (`NVR_NOTIFY_WEBHOOK_URL`, POST JSON
`{"level","key","text"}`, успех — любой HTTP 2xx).

- Дедупликация по инциденту: повторные уведомления по тому же инциденту — не чаще
  `NVR_NOTIFY_REPEAT_SECONDS` (по умолчанию 21600 = 6 часов). RECOVERY отправляется
  только после подтверждённого восстановления и только если инцидент был открыт.
- Токены хранятся только в `/opt/etc/nvr-v2.conf` (mode 600) и передаются в curl
  через stdin-конфиг (`curl -K -`), поэтому не видны в `ps` и не попадают в журналы.
- Ошибка доставки не влияет на запись; неудачная попытка повторяется через интервал.
- `nvr notify test` проверяет доставку и показывает HTTP-коды ответов.
- Если NVR не может отправить уведомление (отключён WAN/роутер/электричество),
  **локальная отправка не гарантирует доставку** именно в тот момент, когда всё
  остальное тоже отключилось. Для контроля «жив ли NVR» извне предусмотрен
  внешний heartbeat через VPS — отдельный вариант, в релиз не входит
  (см. KNOWN-LIMITATIONS.md).

Настройка: интерактивный установщик спрашивает про уведомления при `install-fresh`
(токен вводится скрыто). Для уже установленного NVR — добавить ключи в
`/opt/etc/nvr-v2.conf` и выполнить `nvr notify test`.

## Установка с нуля (другой Keenetic, без старого NVR)

Требования: Keenetic с Entware, отдельный USB-накопитель EXT4 (не системный диск
Entware), интерактивная SSH-сессия (`ssh -t`).

1. Компоненты (установщик предложит установить сам, но можно заранее):

```sh
opkg update
opkg install ffmpeg cron curl coreutils-stat
```

2. Загрузить установщик и проверить окружение (ничего не меняет):

```sh
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-knowledge-base/main/NVR/v2/bootstrap.sh -o /tmp/nvr-install.sh
sh /tmp/nvr-install.sh preflight-fresh
```

Ссылки ведут на ветку `main` и заработают сразу после слияния PR #3; для проверки
ветки-кандидата используйте `NVR_RAW_BASE=https://raw.githubusercontent.com/saymer-alt/keenetic-knowledge-base/nvr/watchdog-v2-candidate/NVR/v2`.

3. Установка:

```sh
sh /tmp/nvr-install.sh install-fresh
```

Мастер на самом роутере: выбор диска из реально смонтированных (системный диск
Entware отвергается) → RTSP-адрес (IP/имя, без `rtsp://` и порта) → логин →
**пароль со скрытым вводом** → каналы (Enter = `101 201 301`) → необязательная
настройка уведомлений. Затем: конфиг `/opt/etc/nvr-v2.conf` (mode 600), старт
FFmpeg, проверка появления свежих MKV каждой камерой (до 60 секунд) и только
потом cron. Cron-задачи других программ не затрагиваются.

**Специальные символы в пароле.** Если пароль содержит `@ : / ? #` и подобные
символы, установщик сам проверит оба варианта URL (как есть и с
процент-кодированием) и сохранит рабочий (`NVR_RTSP_ENCODE`). Буквальный `%`
остаётся как набран в обоих вариантах. Если ни один вариант не подошёл —
используйте отдельную учётную запись камеры с паролем без URL-спецсимволов.

4. Повторная настройка без переустановки (смена пароля/камер):

```sh
sh /opt/etc/nvr-v2.sh stop
sh /tmp/nvr-install.sh configure-fresh
sh /tmp/nvr-install.sh install-fresh
```

## Миграция с NVR v1 (тот же роутер, кнопка `switch`)

Для заранее диагностированного роутера (путь диска совпадает с указанным в
`install-router.sh`): preflight проверяет FFmpeg, `stat`, RW-диск и отсутствие
живых legacy-процессов **до** любых изменений; исходные `S99cctv`, `record_cctv.sh`,
crontab-ы сохраняются в `/opt/etc/nvr-v2-backup`; RTSP-параметры извлекаются из
старого скрипта локально; при сбое — автоматический откат.

```sh
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-knowledge-base/main/NVR/v2/bootstrap.sh -o /tmp/nvr-install.sh
sh /tmp/nvr-install.sh preflight   # только проверка
sh /tmp/nvr-install.sh switch      # переключение
sh /opt/etc/nvr-v2-backup/rollback.sh rollback   # откат, если понадобится
```

После миграции пароль камеры рекомендуется сменить (он уже встречался в старом
скрипте и истории команд) и обновить локально в `/opt/etc/nvr-v2.conf`.

## Обновление существующего NVR v2.x до v2.4

Конфигурация и записи не затрагиваются:

```sh
sh /opt/etc/nvr-v2.sh stop
curl -fSsL <RAW>/nvr.sh -o /opt/etc/nvr-v2.sh && chmod 700 /opt/etc/nvr-v2.sh
sh -n /opt/etc/nvr-v2.sh && sh /opt/etc/nvr-v2.sh start
sh /opt/etc/nvr-v2.sh status
```

Новые ключи конфига необязательны: всё работает и без них (значения по умолчанию —
в `nvr.conf.example`). При обновлении с v2.3 учитывайте новую семантику `stop`
(долгая пауза, см. выше).

## Диагностика типовых ситуаций

- `CAM 101: DOWN` дольше 30 минут → смотреть `nvr logs cam101` и `nvr status`;
  проверить доступность камеры с роутера (`ping`), учётные данные, не занят ли
  канал другим recorder'ом.
- `DISK: NOT MOUNTED/READ-ONLY` → проверьте `mount | grep /tmp/mnt`, файловую
  систему (`dmesg`), кабель/питание USB. Запись и удаление блокируются до
  восстановления RW.
- `LAST CLEANUP: ... FAILED` → обычно совпадает с недоступностью диска;
  повторное выполнение по cron вернёт `OK`.
- `ALERTS: enabled`, но уведомлений нет → `nvr notify test` покажет HTTP-код;
  проверьте токен/chat ID, доступ роутера к api.telegram.org.
- Полный журнал: `nvr logs 200`; место на диске: `df -h /tmp/mnt/<UUID>`.

## Удаление NVR (видеозаписи остаются)

```sh
sh /opt/etc/nvr-v2.sh stop
crontab -l | grep -v 'nvr-v2.sh' | crontab -   # убрать только задания NVR
/opt/etc/init.d/S10cron restart
rm /opt/etc/nvr-v2.sh /opt/etc/nvr-v2.conf
rm -rf /tmp/nvr-v2
# Архив остаётся: /tmp/mnt/<UUID>/cctv/cam*/...mkv — удалить отдельно, если нужно.
```

Для миграции на v1 вместо удаления используйте `rollback` (см. выше).

## Безопасность и секреты

- `/opt/etc/nvr-v2.conf` — mode 600, root-only; токены и RTSP-пароли только там.
- Журналы (`nvr logs`, ротация логов) пропускают RTSP-URL через редактирование:
  `rtsp://…@` → `rtsp://[REDACTED]@`.
- **Известное ограничение:** RTSP-URL с паролем виден в `/proc/<pid>/cmdline`
  процесса FFmpeg любому локальному пользователю с правом чтения `/proc`
  (на Keenetic это root). Ограничение платформы FFmpeg; снижение риска —
  отдельная ограниченная учётная запись только для RTSP. Не публикуйте `ps w`,
  логи камер и содержимое конфига.
- CI репозитория выполняет: синтаксис POSIX sh + BusyBox ash, ShellCheck
  (errors), 5 офлайн-тестов, сканер секретов (токены Telegram, RTSP-URL
  с паролями, приватные ключи).

## Что осталось проверить на живом роутере (после v2.3 cutover)

Офлайн-проверки не заменяют живое испытание; объявлять их выполненными нельзя:

1. Первая фактическая очистка по cron в HH:03 и удаление файлов старше 72 часов
   (не подтверждено на v2.3; в v2.4 добавлен статус `LAST CLEANUP` для контроля).
2. Восстановление одной зависшей камеры без остановки остальных.
3. Поведение после перезагрузки роутера (запись восстанавливается, пауза сохраняется).
4. Чистая установка `install-fresh` на втором Keenetic.
5. Доставка уведомлений Telegram/webhook с реальным роутера (`nvr notify test`).
6. Пригодность созданных MKV (15-минутная нарезка) для воспроизведения/склейки —
   офлайн-стаб не эмулирует реальный контейнер; проверить `ffprobe` на устройстве.

См. также `ARCHITECTURE.md` (устройство) и `KNOWN-LIMITATIONS.md`
(ограничения и backlog).
