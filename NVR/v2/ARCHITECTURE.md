# NVR v2.4 — архитектура и модель состояния

Назначение документа: объяснить, как устроен NVR, какие инварианты он держит и
почему выбраны такие решения. Код (`nvr.sh`) — источник истины; документ следует
за кодом.

## Общая схема

```text
              ┌──────────────── Keenetic + Entware ────────────────┐
 камера/ ─RTSP┐                                                     │
 регистратор  │  cron */5 min ──► nvr.sh check ──┐                  │
 (101/201/301)│  cron 3 * * * * ► nvr.sh cleanup ├─► lock (/tmp)    │
              │                                  │                  │
              │  nvr.sh start/stop/pause/resume ─┘                  │
              │        │                                            │
              │        ▼                                            │
              │  ffmpeg -c copy -f segment (900 s, strftime MKV)    │
              │        │                                            │
              │        ▼                                            │
              └──► /tmp/mnt/<UUID>/cctv/cam<ID>/cam<ID>_YYYY-MM-DD_HH-MM-SS.mkv
                   /tmp/mnt/<UUID>/cctv/.nvr-v2/  — состояние и логи (persistent)
              /tmp/nvr-v2/  — pid/состояние процессов (volatile)
```

Каждый запуск `nvr.sh` — отдельный короткоживущий процесс. Постоянного демона-
watchdog нет: роль watchdog выполняет сам `check` по cron каждые 5 минут.
Все мутации (`check`, `cleanup`, `start`, `stop`) сериализуются mkdir-локом
`/tmp/nvr-v2/.lock` с указанием PID-владельца и повторным использованием
только устаревших (>90 с и с мёртвым PID) ликов.

## Два хранилища состояния

| Расположение | Что лежит | Живёт |
| --- | --- | --- |
| `/tmp/nvr-v2` (`$STATE`) | pid-файлы, `cam*.started`, `cam*.failures`, `cam*.last_try`, пауза, копии state | до перезагрузки |
| `<диск>/cctv/.nvr-v2` (`$PDATA`) | `events.log`, логи FFmpeg камер, `check.state`, `cleanup.state`, `notify.state`, пауза | на USB-диске |

Чтение состояния (`read_kv`) предпочитает volatile-копию (всегда свежая),
после перезагрузки — USB-копию. Запись идёт в оба места атомарно
(временный файл в том же каталоге + `mv`, точка коммита — rename на ext4).
fsync не используется: для этого класса данных потеря последних секунд при
отключении питания приемлема, а синхронный fsync на USB заметно дороже.

**Файлы состояния никогда не исполняются.** USB-диск физически уносим, поэтому
`read_kv` парсит файлы белым списком ключей с жёсткой валидацией форматов
(числа / перечисление OK|PARTIAL|FAILED|NEVER / timestamp `ЦН:ЦН-…`) вместо
`. file`. Подмена файла на диске не даёт выполнения команд.

Формат `cleanup.state`:

```text
CLEANUP_LAST_EPOCH=...        последняя попытка очистки
CLEANUP_LAST_HUMAN=...        в человекочитаемом виде
CLEANUP_RESULT=OK|PARTIAL|FAILED|NEVER
CLEANUP_REMOVED=...           удалено файлов за последнюю попытку
CLEANUP_SKIPPED=...           пропущено из-за ошибок stat
CLEANUP_OK_EPOCH=...          последний полностью успешный запуск (только OK)
CLEANUP_OK_HUMAN=...
```

`PARTIAL` — попытка завершилась, но часть записей не удалось проверить из-за
ошибок `stat` (например, висячий symlink): это не `OK` и показывается в статусе.
`FAILED` — удаление не выполнено (диск недоступен или `rm` потерпел неудачу);
`CLEANUP_OK_*` при этом не обновляется.

## Контракт хранения 72 часов

- Единственный критерий удаления: `mtime < now − NVR_RETENTION_SECONDS`
  (по умолчанию и минимум 259200 = 72 ч). Заполненность диска не участвует.
- Открытый сегмент не удаляется: для камеры с живым процессом (своим по pid-файлу
  или чужим, найденным по `/proc/*/cmdline`) защищён самый свежий файл.
- Очистка часовая → фактическая глубина 72–73 ч; «минимум 72 часа» выполняется
  с запасом.
- Ошибки `stat` по конкретному файлу → файл пропускается и попадает в
  `CLEANUP_SKIPPED` (результат `PARTIAL`); ошибка `rm` → `FAILED`. Тишина или
  «OK» при частичном сбое исключены.
- Прогноз места (`forecast_space`) — только предупреждение: суммарный объём
  записей за последний час × 72 против свободного места. Без свежих данных
  прогноз не строится.

## Watchdog и восстановление

Проверка камеры = процесс (по `/proc/<pid>/exe` это ffmpeg, и конец cmdline
содержит `/Streaming/Channels/<ID>` — совпадение заякорено к концу строки,
чтобы канал 101 не совпал с 1011) **и** свежесть файла (возраст ≤ STALE
с допуском ±STALE на скачок часов назад).

- Процесс мёртв → уведомление ERROR, попытка старта с нарастающей задержкой
  (0/5/10/20/30 мин, счётчик сбрасывается после часа попыток или успешной записи).
- Файл протух (завис поток, нет данных) → после startup grace → ERROR +
  перезапуск только этой камеры (`SIGTERM` → 10 с → `SIGKILL`; FFmpeg при TERM
  закрывает MKV-контейнер с заголовком).
- Дубль записи (два процесса пишут в каталог этой установки) запрещён: найденный
  вне pid-файла процесс, пишущий в `cam<ID>/` этой установки, завершается.
  Чужой recorder (другой каталог) только логируется, не трогается.
- Свежий файл подтверждён → счётчик неудач сброшен, RECOVERY-уведомление
  (только если инцидент был открыт).

## Пауза и жизненный цикл

- `stop`/`pause` — операционное намерение: маркер паузы пишется в `$STATE` и
  (если диск RW) в `$PDATA`, переживает перезагрузку; `check` при паузе — no-op.
  `cleanup` при паузе продолжает работать (хранение 72 ч не зависит от записи).
- `start`/`resume` снимает паузу, сбрасывает задержки повторов и запускает
  немедленный `check`.
- Открытые при остановке инциденты камер закрываются без RECOVERY-шума.
- Восстановление после перезагрузки: cron `check` поднимает камеры на первом
  тике, когда диск смонтирован RW; при отсутствии диска проверка уходит по
  fail-closed и повторяется каждые 5 минут.

## Уведомления

Модель «инцидентов»: ключ (`volume`, `disk-warn`, `disk-crit`, `cam<ID>`,
`cleanup-stale`, `space72`), состояние open/closed и время последней попытки
в `notify.state`. Правила:

- событие уровня проблемы: если инцидент не открыт или прошло ≥
  `NVR_NOTIFY_REPEAT_SECONDS` с последней попытки — отправить, пометить open
  (даже при неудаче доставки — чтобы не долбить сеть каждые 5 минут);
- RECOVERY: только для открытого инцидента и после фактического подтверждения
  (свежий файл / RW-диск / место в норме); при неудаче доставки инцидент
  остаётся открытым;
- форс-эскалация (force=1) — «watchdog не смог восстановить камеру» — один раз
  на цикл счётчика неудач;
- транспорты: Telegram `sendMessage` и/или JSON-webhook; токены и URL
  передаются curl через stdin-конфиг (`curl -K -`) и не появляются в argv,
  журналах или ошибках; таймаут ограничен; любые ошибки доставки не влияют
  на запись.

## Telegram-запросы статуса (необязательный read-only мост)

`telegram-bot.sh` работает отдельно от основного NVR и сам не управляет
FFmpeg. Cron запускает `poll` раз в минуту; Bot API `getUpdates` опрашивается
через HTTPS с кратким timeout, токен проходит только через stdin curl `-K -`.

Для JSON нужен Entware `jq`. Обрабатываются только сообщения в приватном
чате, у которых одновременно `message.chat.id` и `message.from.id` равны
настроенному `NVR_NOTIFY_TELEGRAM_CHAT`. Из внешнего текста выполняется
только сопоставление известных команд (`/status`, `/cameras`, `/disk`, `/help`,
`/start`); произвольные команды shell и NVR write-actions не поддерживаются.

Полученный от NVR вывод `status` сериализуется `jq` в JSON для Telegram
`sendMessage`. Состояние offset, last_poll и lock хранится в
`/opt/var/lib/nvr-telegram` (mode 700), отдельно от временного `/tmp`.
На `init` старые обновления подтверждаются без отправки сообщений.
Обработка и фиксация offset разделены по одному update; после сбоя отправки
необработанный update будет повторён в следующем Cron тике.

Проверка NVR `check` (каждые 5 минут) и отправка аварийных уведомлений
остаются независимыми от Telegram-приёмника. Отключение моста команд
удаляет только его Cron-строку и исполняемый скрипт.

## Гигиена секретов и логов

- RTSP-URL строится из конфига; в логи событий он не попадает никогда.
- FFmpeg-логи могут содержать URL при ошибках RTSP → при ротации (лимит 512 КиБ,
  хвост 256 КиБ) и в выводе `nvr logs` поток проходит через `redact()`:
  `rtsp://user:pass@` → `rtsp://[REDACTED]@` (awk, накопление в отдельную
  переменную — замена не сканируется повторно).
- `/proc/<pid>/cmdline` FFmpeg всегда содержит URL с паролем — платформенное
  ограничение, снижается только отдельной RTSP-учёткой (см. README).

## Почему так (ключевые решения)

- **cron вместо демона**: переживает любые падения самого watchdog, не создаёт
  второй точки отказа; цена — задержка реакции до 5 минут, для архива это
  приемлемо.
- **mtime, а не имя файла**: имя задают время старта сегмента и настройки
  времени устройства; mtime — факт последней записи. Файл с «будующим» mtime
  (перевод часов назад) не удаляется и не считается протухшим в пределах STALE.
- **pid+exe+cmdline вместо «верим pid-файлу»**: PID переиспользуется ядром;
  проверка exe (путь заканчивается на ffmpeg) и якорного канала в cmdline
  исключает убийство чужого процесса с совпавшим PID.
- **mkdir-lock с PID и возрастом**: атомарен в busybox-окружении, сам
  восстанавливается после падения владельца, не удаляет чужой живой лок.
