# NVR v2.4 — известные ограничения, техдолг, backlog

Код — источник истины; таблица отражает состояние на 2026-10-09.
Формат: (риск: High/Medium/Low) описание — рекомендуемое действие.

## Принятые ограничения текущей архитектуры

| # | Ограничение | Риск | Комментарий / действие |
| --- | --- | --- | --- |
| L1 | RTSP-пароль виден в `/proc/<pid>/cmdline` FFmpeg | Medium (локальный root) | Платформенное ограничение FFmpeg RTSP. Смягчение: отдельная RTSP-учётка только для архива; не публиковать `ps w`. Полное решение потребует патча FFmpeg или туннеля — вне рамок |
| L2 | Локальные уведомления не гарантированы при отключении питания/WAN | Medium | Документировано в README; внешний heartbeat через VPS — см. B4 |
| L3 | Реакция watchdog ограничена периодом cron (5 мин) | Low | Принято: разрыв записи до ~5 мин при падении FFmpeg; для архива не критично |
| L4 | Один RTSP-источник (общие IP/логин/пароль для всех камер) | Low | Контракт v1; разные креденшелы на камеру — см. B1 |
| L5 | fsync не выполняется при записи state — потеря последних секунд журнала при сбое питания | Low | Приемлемо для этого класса данных; документировано в ARCHITECTURE.md |
| L6 | `install-router.sh` привязан к конкретному диску домашнего роутера (UUID в пути и IP в комментариях) | Low | Файл миграции одного устройства; не переиспользовать на других роутерах — для них `fresh-install.sh`. UUID — идентификатор раздела, не секрет, но упомянут в сканере секретов |
| L7 | MKV «по 900 секунд» фактически режется по ключевым кадрам | Low | Свойство `-c copy`/segment muxer; контракт «не менее 72 часов» от mtime не зависит от длины сегментов. Воспроизводимость проверить на живом роутере (`ffprobe`) |
| L8 | `owned()`/adopting может усыновить чужой ffmpeg, пишущий тот же RTSP-канал (с другим каталогом вывода) | Low | Одиночный NVR на роутер — рабочее предположение; чужой процесс будет остановлен только при рестарте протухшей камеры |

## Техдолг, обнаруженный при ревью v2.3→v2.4 (исправлено в v2.4)

- `owned()`: grep без якоря конца — канал 101 совпадал с 1011. Исправлено.
- `stop` перезапускался cron'ом. Исправлено (долгая пауза).
- Отсутствие состояния очистки/проверки. Исправлено (state-файлы, атомарная запись).
- README v2.3 содержал вложенную копию самого себя. Исправлено (переписан).
- Парсеры установщиков зависели от формата status. Исправлено (общий контракт
  `CAM <id>: HEALTHY, last write <n>s ago` + тест хелпера).

## Backlog (P2 — сознательно не входит в релиз v2.4)

| # | Идея | Оценка |
| --- | --- | --- |
| B1 | Отдельные IP/логины/пароли на камеру (модель «камера = профиль») | Средняя: новая схема конфига (массив/папка конфигов), правки установщика и `start_cam`; ломает миграцию с v1 — делать отдельным циклом |
| B2 | Другие RTSP-пути помимо `/Streaming/Channels/` | Низкая: параметризовать шаблон URL в конфиге + валидация; влияет на `owned()` (якорь должен учитывать шаблон) |
| B3 | Экспорт метрик (Prometheus node_exporter textfile / JSON-статус) | Низкая: `status` уже машиночитаем по строкам; нужен файл-дамп + cron |
| B4 | Внешний heartbeat/dead-man switch через VPS | Средняя: NVR пишет timestamp «жив» на диск; внешний монитор (VPS) проверяет свежесть и сигналит. Полезно ровно потому, что локальные уведомления (L2) не срабатывают при полной потере роутера |
| B5 | Оценка покрытия архива: сколько *реального* видео доступно за 72 ч по каждой камере (сумма длительностей сегментов, а не просто наличие файлов) | Средняя: длительность сегмента в контейнер не запишешь без ffprobe/duration-парсинга; приближение по сумме размеров и среднему битрейту уже есть в forecast_space |
| B6 | Политика восстановления после длительного отсутствия сети/камеры (например, не молотить стартами, если камера выключена неделями) | Низкая: текущий backoff (≤30 мин) приемлем; возможно добавить «длинный сон» после N суток неудач |
| B7 | Компактная диагностическая команда без секретов (`nvr doctor`) | Низкая: `status` + `logs` уже закрыты редактированием; собрать типовой чеклист в один вывод |
| B8 | Сохранение пользовательских ключей конфига при обновлениях (merge конфига) | Низкая: обновление не трогает конфиг; риск возникает только при переустановке через `configure-fresh` (осознанная замена) |
| B9 | Проверка воспроизводимости MKV (ffprobe) в тестах | Требует реального ffmpeg в CI; офлайн-стаб контейнер не эмулирует — оставить живой проверке (см. README «Что осталось проверить») |

Правило репозитория: незавершённые находки фиксируются здесь (или в Issues),
а не «тихими» правками рабочего кода.
